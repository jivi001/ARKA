# ARKA Phase 2 — OWASP Top 10 (2021) Web/API Traceability

**Status:** Planning cross-reference only. This document does not claim that Phase 2 controls or gates are implemented or passing.  
**Scope:** Phase 2 Execution Broker, broker-facing API, worker protocol, rootless worker and connection policy.  
**Baseline:** `docs/security/PHASE_2_ARCHITECTURE_PLAN.md`; machine-readable security registries remain authoritative for registered threat/control/test/gate IDs.

## Mapping

| OWASP Top 10 (2021) | Phase 2 applicability | Existing ARKA trace / required Phase 2 treatment | Required evidence / status |
|---|---|---|---|
| **A01: Broken Access Control** | Yes — broker API, mission isolation, capability and worker protocol boundaries | Cross-reference existing `GATE-MISSION-ISOLATION-001`, `GATE-SCOPE-ENFORCEMENT-001`, `GATE-DUAL-AUTHORIZATION-001`, `GATE-CAPABILITY-SIGNING-001`, and `GATE-REPLAY-001`. Add a traceability entry for this OWASP mapping when registry/schema changes are reviewed; do not create a duplicate authorization mechanism. | Negative tests for cross-mission access, wrong capability, expired/replayed authorization, and unauthorized worker messages; zero side effects. **Existing gates; mapping documentation added, registry integration pending.** |
| **A02: Cryptographic Failures** | Yes — TLS for worker/broker identity and TLS verification over pinned-IP connections | Add an explicit pinned-dial TLS test: certificate-chain validation remains enabled; the original hostname remains the SNI and certificate identity; invalid, expired, wrong-host and untrusted certificates fail closed. The socket peer must equal the validated IP. | Integration tests against trusted and deliberately invalid test certificates, plus socket-peer assertion. **Required; not yet implemented.** |
| **A03: Injection** | Yes — typed capability parameters, target parsing, worker messages and untrusted output | Add a distinct capability-parameter/parser test class for malformed and oversized hostnames, NUL bytes, CR/LF/control characters, shell metacharacters, invalid ports and ambiguous encodings. Verify typed capability models reject invalid values before dispatch and never convert user data into command strings. | Unit/property/fuzz tests; assert invalid input is rejected and no socket/process side effect occurs. **Required; not yet implemented.** |
| **A04: Insecure Design** | Yes — covered by the phase threat→control→test→gate approach | Maintain the Phase 2 plan's fail-closed boundaries, one authorization authority, single destination-validation/pinned-dial path, and explicit release gates. | Architecture review and adversarial review; no standalone new gate proposed here. |
| **A05: Security Misconfiguration** | Yes — rootless runtime, seccomp, AppArmor, namespaces, mounts and egress policy | P2-C must fail worker startup if required seccomp or AppArmor policy cannot be loaded/applied. No silent fallback, “best effort” mode, or execution with a missing required profile. If AppArmor is explicitly unsupported on a declared CI/development platform, document the platform-specific policy decision and test the alternative enforced boundary; do not report AppArmor as active. | Negative integration test with invalid/missing profile and observable worker-start refusal; record effective runtime/profile configuration. **Required; not yet implemented.** |
| **A06: Vulnerable and Outdated Components** | Yes | Existing plan requires locked dependencies, pinned rootless runtime/helper versions and image digests where applicable, provenance, vulnerability scans and a documented update/exception process. | CI artifacts, SBOM/scans, version/digest evidence and reviewed exceptions. **Covered by plan; execution evidence still required.** |
| **A07: Identification and Authentication Failures** | Yes — worker↔broker protocol | P2-A decision: use TLS 1.3 mutual TLS with an ephemeral per-execution worker identity under the existing `WORKER-IDENTITY` key domain and existing Ed25519-capable key-provider primitives. Do not reuse the `TOKEN-SIGNING` private key or create a parallel bearer-token scheme. Bind authenticated peer identity to execution ID, mission ID, capability and a fresh request/nonce; reject expired, revoked, wrong-mission and replayed identities. Final implementation must be reconciled with the actual Rust TLS/provider APIs. | Tests for missing/wrong client certificate, wrong peer identity, cross-mission identity, expired identity, replay, broker impersonation and certificate-validation failure. **Architecture decision recorded here and in the Phase 2 plan; implementation pending.** |
| **A08: Software and Data Integrity Failures** | Yes — typed worker protocol, evidence and audit boundaries | Worker protocol deserializers must use strict unknown-field rejection (for Serde structs, `deny_unknown_fields` where applicable), explicit protocol-version handling, maximum frame/message bytes, bounded field lengths and bounded nesting/depth. Reject malformed, truncated, trailing or unsupported messages before state changes. Keep output untrusted and evidence integrity checks separate from authorization. | Negative parser tests and fuzzing for unknown fields, excessive depth/size, duplicate/ambiguous fields, malformed encoding and truncation. **Required; not yet implemented.** |
| **A09: Security Logging and Monitoring Failures** | Yes | Existing P2-F audit/evidence requirements cover dispatch decisions, worker lifecycle, network denials, timeouts, cleanup and emergency stop. Audit failure must fail closed where the operation requires durable audit. | Lifecycle completeness, audit tamper detection and audit-store-failure tests. **Covered by plan; execution evidence still required.** |
| **A10: Server-Side Request Forgery (SSRF)** | Yes — central Phase 2 risk | Existing `GATE-SSRF-001`, `GATE-DNS-REBIND-001`, `GATE-METADATA-BLOCK-001`, `GATE-IPV6-POLICY-001`, and `GATE-REDIRECT-FILTER-001`. Every redirect hop must use the same destination-validation and pinned-dial path as the first hop. | Socket peer equals validated IP; packet-capture-backed absence of prohibited side effects; rebinding, parser-differential, metadata and redirect tests. **Covered by plan; execution evidence still required.** |

## Gate and registry discipline

1. This is a human-readable cross-reference, not a replacement for `security/threat-model/threats.yaml`, `security/controls/controls.yaml`, `security/tests/tests.yaml`, `security/acceptance/gates.yaml` or `security/traceability/security-traceability.yaml`.
2. A new blocking gate or test ID must be added to the appropriate registries with a unique ID, linked threat/control/test, schema-valid fields and evidence requirements. Update the validator and baseline manifest as required; do not treat a prose row as a passing gate.
3. Keep all newly described controls in a pending/not-implemented state until code and CI evidence exist. No status in this document authorizes target execution.
4. OWASP categories are a coverage lens, not a claim of certification or complete security. Phase 2 acceptance remains governed by ARKA's own threat model and blocking gates.
