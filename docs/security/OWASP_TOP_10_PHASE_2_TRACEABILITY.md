# ARKA Phase 2 — OWASP Top 10:2025 Web/API Traceability

**Status:** Planning cross-reference only. This document does not claim that Phase 2 controls or gates are implemented or passing.  
**Scope:** Phase 2 Execution Broker, broker-facing API, worker protocol, rootless worker and connection policy.  
**OWASP baseline:** [OWASP Top 10:2025](https://top10.owasp.org/2025/), the latest released OWASP Top 10 for web application security as of 2026-10-09. OWASP has not published a separate web-application Top 10:2026 edition in the official project resources.  
**ARKA baseline:** `docs/security/PHASE_2_ARCHITECTURE_PLAN.md`; machine-readable security registries remain authoritative for registered threat/control/test/gate IDs.

## Mapping

| OWASP Top 10:2025 category | Phase 2 applicability | Existing ARKA trace / required Phase 2 treatment | Required evidence / status |
|---|---|---|---|
| **A01:2025 — Broken Access Control** | Yes — broker API, mission isolation, capability and worker protocol boundaries; SSRF is included in this category in the 2025 taxonomy | Cross-reference existing `GATE-MISSION-ISOLATION-001`, `GATE-SCOPE-ENFORCEMENT-001`, `GATE-DUAL-AUTHORIZATION-001`, `GATE-CAPABILITY-SIGNING-001`, `GATE-REPLAY-001`, `GATE-SSRF-001`, `GATE-DNS-REBIND-001`, `GATE-METADATA-BLOCK-001`, `GATE-IPV6-POLICY-001` and `GATE-REDIRECT-FILTER-001`. Every redirect hop must use the same destination-validation and pinned-dial path as the initial request. Add the OWASP cross-reference to machine-readable traceability in a reviewed registry/schema change; do not create a duplicate authorization mechanism. | Negative tests for cross-mission access, wrong capability, expired/replayed authorization and unauthorized worker messages; SSRF/DNS/metadata/IPv6/redirect tests must assert socket-peer binding and absence of prohibited side effects. **Existing gates; 2025 mapping documented, registry integration pending.** |
| **A02:2025 — Security Misconfiguration** | Yes — rootless runtime, seccomp, AppArmor, namespaces, mounts and egress policy | P2-C must fail worker startup if a required seccomp or AppArmor policy cannot be loaded/applied. No silent fallback, “best effort” mode, or execution with a missing required profile. If AppArmor is unavailable on a declared platform, document the platform-specific decision and prove the alternative enforced boundary; never report AppArmor as active when it is not. | Negative integration test with invalid/missing profile and observable worker-start refusal; record effective runtime/profile configuration. **Required; not yet implemented.** |
| **A03:2025 — Software Supply Chain Failures** | Yes — Rust dependencies, worker runtime, helper binaries, build and distribution artifacts | Existing plan requires locked dependencies, pinned rootless runtime/helper versions and image digests where applicable, provenance, vulnerability scans and a documented update/exception process. Include the runtime and worker image in CI scanning. | CI artifacts, SBOM/scans, version/digest and provenance evidence, plus reviewed exceptions. **Covered by plan; execution evidence still required.** |
| **A04:2025 — Cryptographic Failures** | Yes — TLS for worker/broker identity and TLS verification over pinned-IP connections | Add a pinned-dial TLS test: certificate-chain validation remains enabled; the original hostname remains the SNI and certificate identity; invalid, expired, wrong-host and untrusted certificates fail closed. The socket peer must equal the validated IP. | Integration tests against trusted and deliberately invalid test certificates, plus socket-peer assertion. **Required; not yet implemented.** |
| **A05:2025 — Injection** | Yes — typed capability parameters, target parsing, worker messages and untrusted output | Add a distinct capability-parameter/parser test class for malformed and oversized hostnames, NUL bytes, CR/LF/control characters, shell metacharacters, invalid ports and ambiguous encodings. Verify typed capability models reject invalid values before dispatch and never convert user data into raw command strings. | Unit/property/fuzz tests; assert invalid input is rejected and no socket/process side effect occurs. **Required; not yet implemented.** |
| **A06:2025 — Insecure Design** | Yes — trust boundaries and fail-closed execution design | Maintain one authorization authority, a single destination-validation/pinned-dial path, explicit release gates, dispatch idempotency and fail-closed behavior. Keep kernel-side budget decisions distinct from OS-enforced worker resource limits. | Architecture/adversarial review; test authorization, retry/crash and resource-exhaustion paths. No separate new gate proposed solely by this mapping. |
| **A07:2025 — Authentication Failures** | Yes — worker↔broker protocol | P2-A decision: use TLS 1.3 mutual TLS with an ephemeral per-execution worker identity under the existing `WORKER-IDENTITY` key domain and existing Ed25519-capable key-provider primitives. Do not reuse the `TOKEN-SIGNING` private key or create a parallel bearer-token scheme. Bind authenticated peer identity to execution ID, mission ID, capability and a fresh request/nonce; reject expired, revoked, wrong-mission and replayed identities. Reconcile with the selected Rust TLS/provider APIs before implementation. | Tests for missing/wrong client certificate, wrong peer identity, cross-mission identity, expired identity, replay, broker impersonation and certificate-validation failure. **Architecture decision recorded; implementation pending.** |
| **A08:2025 — Software or Data Integrity Failures** | Yes — typed worker protocol, evidence and audit boundaries | Worker protocol deserializers must use strict unknown-field rejection (for Serde structs, `deny_unknown_fields` where applicable), explicit protocol-version handling, maximum frame/message bytes, bounded field lengths and bounded nesting/depth. Reject malformed, truncated, trailing or unsupported messages before state changes. Keep output untrusted and evidence integrity checks separate from authorization. | Negative parser tests and fuzzing for unknown fields, excessive depth/size, duplicate/ambiguous fields, malformed encoding and truncation. **Required; not yet implemented.** |
| **A09:2025 — Security Logging and Alerting Failures** | Yes — dispatch decisions, worker lifecycle, policy denials and cleanup | Existing P2-F audit/evidence requirements cover dispatch decisions, worker lifecycle, network denials, timeouts, cleanup and emergency stop. Audit failure must fail closed where the operation requires durable audit; security-relevant failures must be surfaced through the defined audit/alerting path without leaking secrets. | Lifecycle completeness, audit tamper detection, audit-store-failure tests and evidence that security-relevant failures are surfaced. **Covered by plan; execution evidence still required.** |
| **A10:2025 — Mishandling of Exceptional Conditions** | Yes — DNS/connect races, redirects, cancellation, worker crashes, timeouts, cleanup and uncertain dispatch outcomes | Fail closed on resolver/connector errors, partial protocol messages, timeout, worker termination, audit persistence failure and emergency stop. Do not automatically re-execute an action when crash recovery leaves its side-effect outcome uncertain. Test emergency stop during DNS-validation-to-connect and during pinned connect. SSRF remains cross-referenced under A01 in the 2025 taxonomy. | Fault-injection and race tests for timeout, crash, cancellation, cleanup failure, audit failure and e-stop; prove no unauthorized retry or prohibited side effect. **Required; not yet implemented.** |

## Gate and registry discipline

1. This is a human-readable cross-reference, not a replacement for `security/threat-model/threats.yaml`, `security/controls/controls.yaml`, `security/tests/tests.yaml`, `security/acceptance/gates.yaml` or `security/traceability/security-traceability.yaml`.
2. A new blocking gate or test ID must be added to the appropriate registries with a unique ID, linked threat/control/test, schema-valid fields and evidence requirements. Update the validator and baseline manifest as required; do not treat a prose row as a passing gate.
3. Keep all newly described controls in a pending/not-implemented state until code and CI evidence exist. No status in this document authorizes target execution.
4. OWASP categories are a coverage lens, not a claim of certification or complete security. Phase 2 acceptance remains governed by ARKA's own threat model and blocking gates.
5. This mapping uses OWASP Top 10:2025 category names and grouping. In particular, SSRF is included under A01:2025 rather than being a standalone A10 category as it was in 2021.
